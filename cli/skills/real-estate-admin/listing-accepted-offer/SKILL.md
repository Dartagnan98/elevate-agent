# Listing Accepted Offer

## Accepted-offer transaction creation rule

When an accepted offer is received, create or find the SkySlope transaction. Do **not** stop transaction creation solely because a listing-agent phone number is missing. If SkySlope allows the phone field to be blank, unknown, or safely skipped, proceed, document the missing phone in the output, and upload the verified accepted-offer documents when the verification gate passes. Do not final-submit compliance or use fabricated contact details.

**SkySlope listing-agent phone blocker pitfall.** In the new SkySlope transaction `/agents` step, the listing-agent phone field can become `Required` and disable Continue even though the listing-agent phone was not in the CPS/email evidence. Do not invent a phone number and do not try to bypass the disabled Continue. First check existing Elevate contacts, deal artifacts, CPS notice section, and prior Gmail/router manifests for a verified phone. If online lookup is needed, use local/free Browser Use CLI only; search engines may present bot challenges, so prefer direct brokerage/agent pages or already-captured source artifacts. Direct brokerage advisor pages can be enough evidence: in one recovery, Google and DuckDuckGo both challenged, but the brokerage's own advisor-directory page loaded through Browser Use; searching the listing agent's name on that page surfaced a verified phone number, which cleared the SkySlope `/agents` required phone field and enabled Continue. If no verified phone is found, stop as `waiting_human` with the exact missing field, the current SkySlope draft URL/transaction token, and screenshot/artifact paths; do not upload or final-submit documents until the contact gate is resolved and the transaction/checklist page can be read back.

**SkySlope commission-entry pitfall in new React transaction flow.** The Commission step may default to `Tiered` and expose a required `additional sales commission` field where entering `0` is invalid (`Must be a positive number`), leaving Continue disabled even when the calculated sale commission is correct. Do not force invalid zeros. If the signed expected-remuneration evidence is tiered, first try leaving the additional field truly blank or using the UI's clear/delete controls; if the field cannot be cleared and Continue remains disabled, preserve a screenshot/state dump and stop rather than submitting a distorted commission. Switching to `Flat` without toggling the `%/$` control can treat the entry as a percentage (`11025` becomes invalid `Must be less than 100` and calculates an impossible commission), so only use Flat after confirming the control is set to `$`, then verify the commission breakdown and read-back after Continue/reload. **Recovery from a wrong Flat attempt:** if the page shows Flat selected, sale field `11,025`, error `Must be less than 100`, and an impossible commission breakdown, switch back to `Tiered`, enter the actual signed percentages from the remuneration disclosure/listing terms, leave `additional sales commission` blank, and confirm the breakdown before continuing. In one such recovery, the correct fix was Tiered sale commission `3%` on first `$100,000` and `1.5%` on the balance, additional blank, producing the expected total; then Continue advanced to the deposit step. On the deposit step, choose brokerage holds trust money when eXp will hold it, enter the deposit amount/due date from the verified CPS, and **after Create Transaction read back the legacy checklist header**. Record the new transaction handle (e.g. `TransactionChecklist.aspx?TransactionID=...`), status, checklist type, sale price, buyer/seller, subject removal date, and any unexpected header value such as an acceptance date that differs from the CPS final-acceptance date before uploading any checklist documents.

## ⛔ FILING VERIFICATION GATE — run FIRST, and never claim done without it

MANDATORY before any document is selected, filled, uploaded, filed, sent, or treated as
accepted, and before any calendar event, status change, checklist mark, or client send.
Build the `verification` artifact below, attach it to the deal, and include it in the
output contract. **Never report done / fixed / accepted / firm / sold / uploaded / sent
unless `verification.status == "passed"`.** "Passed" means every sub-check for the
surfaces this task touched is satisfied with recorded evidence. If any required check
cannot be satisfied with visible evidence, STOP and return `waiting_human` with the
exact blocker. Apply only the sub-checks relevant to what this task actually does (a
draft-only run skips the persistence sub-check; a run that doesn't touch included/excluded
items skips that sub-check) — but you may not skip a sub-check for a surface you DID touch.

1. **Side.** State SELLER-side (the realtor represents the seller / her listing) or BUYER-side
   (she represents the buyer). Every template, checklist, and email is side-specific.

2. **Active transaction.** Confirm you are on the ACTIVE, non-cancelled transaction — never
   the first/cancelled search result. Record its id and the observed status (e.g. Incomplete,
   NOT Canceled/App).

3. **Parties from the contract body.** Read the CPS body (not the signature block) and list
   every named buyer and every named seller, with the page where they are named. Then list
   any party currently on the file / SkySlope header that is NOT in the current CPS — those
   are stale/collapsed-sale leftovers (e.g. an old buyer from a cancelled deal) and must be
   removed; they may not remain.

4. **Execution per party, per required page (visual).** Render the signature/initial pages
   (pdftoppm / contact sheet) and visually confirm — text extraction shows printed names
   even when the line is blank, so OCR/vision the actual marks. For EVERY named party,
   record which initial pages are required vs which are present, and whether the signature
   is present. A document is fully executed only when, for every named party, required
   initial pages == present initial pages AND signature is present. Reject any version
   missing a party's marks. An emailed PDF is not a signed envelope; subjects like "Signing
   complete" / "Envelope completed" are NOT proof.

5. **Acceptance.** A CPS is accepted only when BOTH sides have fully executed and a Section 28
   final-acceptance date exists. Buyer-signed-only is a PENDING seller-signature package, not
   an accepted offer — handle it as a draft/handoff and stop. (This is true regardless of
   which side the realtor represents — side controls the template, not whether seller execution
   is required.)

6. **Select exactly one** fully-executed document that passed 3–5. If none passes, STOP
   (`waiting_human`). Never file a partially-executed CPS.

7. **Template/checklist matches side** (only if you send a checklist/email or mark a
   checklist). The selected Mailjet template / checklist must match the side from step 1
   (seller-side → the Seller Accepted Offer template, not a buyer checklist). Record the
   template id/name and that it matches the side.

8. **Terms transcribed verbatim** (only if you fill contract terms). Copy included items and
   excluded items from the CPS exactly as listed, under the heading each appears under — do
   NOT merge, normalize, or infer which list an item belongs to. Record each with its
   section reference. Same discipline for price, deposit, and dates.

9. **Agent/brokerage identity** (only if you fill agent/office fields). Each agent line's
   office address / license / contact must belong to the agent NAMED on that line — never
   paste one agent's office address under a different agent's name. Add required dates next
   to each signature/initial line; add a signature only where that party actually signs.

10. **Persistence — verify the write, not the exit code** (only if you wrote/uploaded
    anything). After every write/upload, RE-READ the actual persisted value (portal row
    status, attached filename / HFFileName, the field value after reload) — a browser script
    can report failure when the row advanced, or success when nothing persisted. Record
    observed vs expected per write. No "done/uploaded/filed/sent" claim is allowed unless
    every write this run performed has a verified read-back.

## Safety

- Verify the deal/listing by exact property address **and active transaction status** before writing in SkySlope. If SkySlope shows multiple transactions/listings for the same address, never assume the first search result is the current file. Click **Transactions / View Transactions** to view active transactions, compare deal numbers, status labels, close date, buyer/seller names, and checklist type, and explicitly avoid archived/cancelled files such as `Canceled/App` unless the task is specifically to audit that old collapsed file.
- For properties with a prior collapsed sale, treat any cancelled/archived transaction as read-only by default. Do not add new accepted-offer details, contacts, commission, documents, or checklist work to the cancelled file. If data was accidentally added to the wrong file, stop, document what changed, locate the active transaction through **View Transactions**, and continue only in the active file. Do not delete or alter archived compliance records without the realtor's explicit approval.
- Recovery pattern from one collapsed-sale run: the active transaction was not visible from the cancelled file path. From SkySlope home / agent dashboard, go to **View Transactions / Transactions** and locate the active/current row. The correct active row showed the current property address, close date, and a URL of the form `CreateTransaction.aspx?TransactionID=...&ListingID=...&checklistId=...`; later portal verification showed the active transaction as `Pending`. The stale/cancelled file used a different `TransactionID` and displayed `Canceled/App`; it belonged to the prior collapsed sale and its historical buyer. When recovering, audit both logs/read-only if needed, but write only to the active transaction found from **View Transactions / Transactions**. The current CPS controls buyer identity; the current buyers and sellers named on the signed CPS supersede whatever the stale file shows. Remove the old buyer from the active/current file when they appear there as leftover collapsed-sale data. Upload/migrate current accepted-offer documents and the approved-template Deal Sheet (TRS) into the active transaction only, then verify checklist row status and attachment names. Buyer conditions for this accepted offer remained active during the recovery run, so do **not** mark firm/sold/unconditional or complete subject-removal tasks merely because the TRS is being corrected. Do not delete, annotate, submit, or otherwise clean up the cancelled transaction unless the realtor explicitly approves a compliance cleanup path.
- Retrieve and inspect the fully signed Contract of Purchase and Sale (CPS) before filling fields.
- When multiple names appear on either the buyer side or seller side, verify the CPS has enough initials/signatures for every named party before selecting, uploading, or treating it as accepted. Reject/skip versions that only show one party’s initials when multiple buyers/sellers are named.
- If the recovered package is a buyer-signed counter/new Offer 2 that still needs seller review/signatures, do **not** run the accepted-offer SkySlope/calendar/deal-field workflow yet. Treat it as a seller-signature package prep task: create a new draft-only DigiSign/SkySlope envelope from the exact newest PDF, place seller initials/signatures/final-acceptance-date fields, preview/verify it, and stop for human approval before sending.
- Use the signed contract as source of truth for buyer/seller names, accepted price, deposit, dates, subjects, agency, and included terms. When a prior sale collapsed, old buyer/client information from the collapsed transaction is not controlling for the new accepted offer. In the active/current transaction, remove old non-proceeding buyer information when the realtor confirms it is from the collapsed sale, and replace it with the buyer(s) on the current signed CPS.
- SkySlope contact correction quirk observed on a collapsed-sale recovery: the left header can continue showing the old buyer until the current buyer contact edits are saved and the Transaction tab is reloaded. On the Contacts page, click Buyer/Tenant, edit buyer 1, change names, add a note documenting the correction, add the second buyer with New Buyer if needed, and save the newly added buyer first if SkySlope validation complains about a blank buyer. Then save the edited first buyer and verify persistence by navigating to `CreateTransaction.aspx?...` and reading the header buyer block. Do not rely on the editable Contacts page alone as proof.
- For seller-represented accepted offers, prepare/send the **seller accepted-offer checklist** from the Mailjet template, not a buyer accepted-offer checklist. Buyer checklist language is only for buyer-side representation. Use the realtor's approved seller Mailjet template unless a newer approved seller accepted-offer template supersedes it. Processing the accepted offer is not complete until the seller accepted-offer Mailjet state is recorded as sent/proofed or explicitly blocked with a waiting-human reason. If the realtor's current instruction says `send` or the workflow trigger itself carries standing send approval, send after recipient/template verification and do not create a duplicate approval prompt for the same email. If she says `draft`, draft/proof only.
- External sends, signature requests, MLS publish/activation, final compliance submit, and destructive changes require human approval.
- **Uploading an already-signed document (signed CPS, Deal Sheet/TRS, MLS sheet, etc.) to a SkySlope checklist row is a SAFE INTERNAL FILING action and does NOT require approval. Do it automatically as soon as the paperwork is verified. Never park an accepted-offer run at `waiting_human` just to ask permission to file a signed doc to SkySlope. Only the SkySlope final submit/complete button (the one that changes transaction phase or notifies external parties), external sends, and signature sends are gated. Uploading a document is not a "portal side effect" for approval purposes.**
- When mirroring the signed documents back to the deal's Google Drive folder (the card **Documents** tab), file **EACH signed document as its own separate PDF**, pulled per-document from the SkySlope checklist rows — never the single merged DigiSign "Envelope completed" PDF (that gives one combined file the realtor cannot work with). Follow the `skyslope-sync` rule "Filing signed / completed documents to the deal's Drive folder — SEPARATE PDFs, one per document."
- If SkySlope has a final submit/complete button that changes transaction phase or notifies parties, stop and ask unless the realtor explicitly approved that exact action.

## Workflow

1. Match the deal/listing with `deal-matcher` using exact property address and any MLS/listing identifiers.
2. Locate the signed CPS in SkySlope/DigiSign/Drive. Download or save evidence of the signed document.
   - If there are multiple CPS versions, compare initials/signatures before choosing one.
   - Count named buyers and sellers, then confirm initials/signatures cover every named party (e.g., two sellers require both sellers’ initials such as JP and CB throughout applicable pages).
   - If a later email/package arrives after a deal is already in Accepted Offer/Condition Removal, treat it as a possible new counter/Offer 2. Do not overwrite the existing accepted-offer track until seller signatures/final acceptance are confirmed. Keep the board status as prior accepted terms, attach a pending-seller-signature offer review, and clearly flag the out-of-sync/new-offer status.
   - If the realtor asked to send the offer to the clients for signatures and the newest PDF is buyer-signed only, build a fresh seller-signature draft from that newest PDF only. Do not reuse an older DigiSign draft/envelope tied to an earlier Gmail message or source PDF. Flag any seller email mismatch before send approval, but you may still create and preview the draft.
3. Extract a contract summary:
   - property address
   - buyers
   - sellers
   - purchase price
   - deposit amount and due terms
   - completion date
   - possession date/time
   - adjustment date
   - subject/removal dates and major conditions
   - final acceptance date
   - included/excluded items and addenda
4. Immediately create accepted-offer due-diligence reminders/tasks for the listing:
   - order the BIR / Building Information Report when the CPS calls for it
   - check whether all strata documents are already on file, and order any missing strata documents
   - order non-financial title charges / legal notations for buyer title review; do not order mortgage charges or other financial charges unless the realtor specifically asks
   - If LTSA/title-charge ordering is blocked because the realtor needs to add funds/money first, do **not** mark title charges as ordered or imply external ordering happened. Pause the deal checklist/status explicitly, for example `workflow_title_charges_ordered_date = paused_pending_funds` and `workflow_title_charges_ordering_status = paused_pending_realtor_adds_funds_no_charges_ordered_YYYY-MM-DD`, then verify deal events show only internal status/toggle changes and no title-ordering/external-send action.
   - If the buyer side asks for “all legal notations and title charges,” do **not** treat the title search print alone as complete. Open the title, extract every highlighted/registered legal notation and charge number, then order/retrieve the separate LTSA instrument documents for each requested registration number unless the realtor explicitly says the title print is enough. For strata title requests like this, this includes covenant, statutory right of way, party wall agreement, modification, and other highlighted registration numbers shown on the title search.
5. Automatically populate the realtor's Google Calendar from the signed CPS dates:
   - subject removal / condition removal deadline(s), including the exact time if stated
   - deposit due date/time, calculated from the CPS terms when written as a relative deadline such as within 24/48 hours of acceptance or subject removal
   - completion date
   - possession date/time
   - adjustment date, if different from completion
   - any inspection, financing, insurance, document-review, title-review, or strata-document deadlines that are expressly written as subject deadlines in the CPS
   Use the property address in every calendar title, include the accepted-offer deal link/context in the notes when available, and do not create duplicate events if matching events already exist.
6. Open the listing record in SkySlope and click **Accepted Offer**.
5. Fill fields from the signed CPS only. Do not guess missing values.
6. As part of the same accepted-offer workflow, fill the realtor's approved deal-sheet form/template only. Do not create a new substitute deal sheet layout. Use the approved historical/template deal sheet from the shared team brain or saved approved form as the source layout, populate it from the signed CPS and signed listing commission terms, then attach it to the **Deal Sheet (TRS)** checklist row unless required deal-sheet data is missing. Do not treat a local/upload-ready TRS PDF as completion proof by itself: after upload, reopen/refresh the active SkySlope checklist and verify the exact **Deal Sheet (TRS)** row changed from `Required` to attached / In Review / Completed, with the current document visible on that row.
7. Also automatically retrieve the **MLS Sheet w/Commission (Realtor Version)** from AOIR/Xposure/Matrix using the MLS number first, or exact civic address if MLS is missing, and attach it to the **MLS Sheet w/Commission (Realtor Version)** SkySlope checklist row.
8. Prepare/upload **Disclosure to Seller of Expected Remuneration** for the accepted offer as the normal/default rule. Only when the realtor states the deal involved multiple offers, prepare/upload one expected-remuneration disclosure for every submitted offer, including non-accepted offers, using each offer's price and cooperating brokerage terms. Attach each disclosure to the appropriate disclosure/remuneration/compliance checklist row, and do **not** upload these disclosures into unrelated checklist rows.
9. Never attach the CPS/Contract of Purchase and Sale to the **Office Deposit Receipt** row. The Office Deposit Receipt row is only for the brokerage/office deposit receipt after deposit handling evidence exists. CPS belongs on the Contract of Purchase and Sale checklist row.
10. For seller-side accepted offers on the realtor's own listings, prepare the Mailjet seller accepted-offer email using the realtor's approved seller accepted-offer template. Review the accepted CPS/contract first and prefill the template as much as possible:
   - `firstname`
   - `property_address`
   - `accepted_price`
   - `subject_removal_date`, or mark not applicable if the contract is subject-free
   - `deposit_due_date`, calculated from CPS terms when relative to subject removal/acceptance and excluding weekends/stat holidays when required
   - `completion_date`
   - `possession_date`
   - inspection timing if agreed; otherwise say the realtor will communicate once she finds out when the inspection is
   - document-ordering note: the realtor/admin will order/collect required documents, so sellers do not have to worry about that
   - main seller decision needed: who they want to use for lawyer/notary
   - approved lawyer/notary referral list the realtor has on file for the buyer-side accepted-offer email (name + phone for each)
   Ask the realtor only for missing information needed to send the email fully filled out. Create/send a proof for review first; do not send client-facing email until the realtor approves the proof.

Mailjet transactional `TemplateLanguage` variables do **not** replace those reliably in test/client sends. For proofs and one-off client sends, pre-render the approved template HTML/text by replacing all `[[data:...]]` fields manually, replace or remove `[[UNSUB_LINK_EN]]`, and verify no `[[data:` or `[[UNSUB` placeholders remain before sending via `HTMLPart`/`TextPart`. Save rendered artifacts under the property/deal folder when the edits are deal-specific, or under `data/marketing/mailjet/` only for reusable template artifacts.

If the realtor asks for revisions after a proof and says it is a one-time edit, modify only the rendered deal-specific HTML/text artifact and do not update the source template.
13. When revising seller accepted-offer proof copy from the realtor's voice/text notes, preserve her substance directly: status of RTB-10/park manager/site lease/interview scheduling, BIR/document ordering responsibility, unknown inspection timing, tax notice request, professional cleaning coordination, and lawyer requirements. Do not generalize away these operational specifics.
14. When sending the approved seller accepted-offer email to multiple sellers, send separate Mailjet messages to each seller so their email addresses are not exposed to each other. Use each seller's preferred first name in the greeting.
15. If the realtor asks to email accepted-offer documents to a mortgage broker, conveyancer, lender, lawyer/notary, client, co-operating agent, or any other recipient, treat it as an external send that still needs a complete recipient and attachment audit before sending:
   - **Fully signed CPS default:** when the realtor asks for accepted-offer/CPS/documents to be sent, attach the **fully signed CPS / accepted offer** unless she explicitly says to use a buyer-signed, seller-signed-only, draft, half-signed, or other partial version. Never attach a half-signed/partially signed CPS as the default.
   - Before attaching any CPS, verify the selected PDF is fully signed by checking the property address, buyer/seller names, final acceptance/offer signatures, and that initials/signatures cover every named buyer and seller. If multiple CPS versions exist, reject/skip partial or superseded versions and choose the newest fully signed version; if none can be verified, hold the send and report the blocker.
   - **CC rule:** CC the realtor on every outgoing Admin email unless she explicitly says not to. For Mailjet/templated sends, include the realtor as a CC when the provider/template supports CC; if not supported, create/record an internal copy or separate proof to the realtor and clearly report the limitation before marking the send complete.
   - Match the recipient by exact name/email from Gmail search/history first. Example pattern: search Gmail for the quoted recipient name, then inspect recent message metadata to recover the address. Do not rely on memory alone.
   - Match the property by exact civic address in Drive and Gmail. For manufactured-home deals, the package may need the signed CPS/accepted offer, CPS manufactured-home rental-pad form, CPS addendum, PDS, Mobile Home Registry/MHR, and the MLS sheet.
   - Download candidate PDFs from Drive with `gws drive files get --params '{"fileId":"...","alt":"media","supportsAllDrives":true}' --output file.pdf`, then verify file sizes and use `pdftotext`/`pdfinfo` to confirm the address, MLS number, and full signature status before attaching.
   - If `google-workspace` setup fails under the system `python` because it is Python 3.9 or older, use `/Users/admin/.local/bin/python3.11` for the skill scripts, or call `gws` directly with `GOOGLE_WORKSPACE_CLI_KEYRING_BACKEND=file`.
   - Drive search may not find an MLS sheet by `MLS`, `listing`, or MLS number even when the CPS contains the MLS number. If the MLS sheet is missing after searching the property folder, Drive fullText by civic address, Gmail by address + `filename:pdf`, and the MLS number from `pdftotext` on the CPS, stop and tell the realtor exactly which attachments were found and that the MLS sheet is still missing. Do not silently substitute the CPS page that lists the MLS number for the MLS sheet.
   - When all documents are present, draft the email in the realtor's voice, attach PDFs directly when small enough, and get approval before sending unless the realtor has explicitly approved that exact external send in the current context.

14. Stop before final submission if it notifies external parties, requests signatures, sends client-facing email, or locks the workflow; create a concise human prompt listing what was filled and what needs approval. ## Pitfalls

- A regular emailed PDF is not the same as a DigiSign/SkySlope signed envelope. Confirm signed status/evidence in the provider.
- A buyer-signed offer/counter received by email is not a seller-accepted CPS just because the deal already has an accepted-offer stage. If seller signature/initial/final-acceptance fields are blank, prepare a seller-signature handoff only: source email/package, terms, recipients, required placements, blockers, and exact next actions. Do not update accepted price/dates or calendar from the new terms until the fully seller-signed package is attached.
- Never reuse or send an existing DigiSign/SkySlope draft until its source PDF/message ID matches the current offer package. A prior draft can have valid recipients/placements but still be for the wrong version. Compare source PDF path, Gmail message ID/thread, file hash/page count, and key terms before sending.
- A delegation/background-task failure such as `'dict' object has no attribute 'lstrip'` may be in the wrapper (`delegate_tool._looks_like_error_output`) rather than the real estate workflow. Recover by reading deal attachments/events, local artifacts, and logs, then continue the review manually instead of assuming the package review failed.
- A DigiSign/SkySlope signed envelope can still be the wrong version if it lacks every named party’s initials/signatures. For accepted offers with multiple sellers/buyers, search/count initials in the PDF text and visually spot-check signature/initial blocks; do not upload a one-initial version when multiple sellers/buyers are named.
- Multiple contacts with similar names can exist; match the transaction by property address and contract, not first name.
- Do not rename an attached SkySlope buyer/contact record just because a superseding offer has different buyer names. Existing attached contacts may be shared/global records; replace/remove buyer contacts only after explicit human approval or after verifying the exact intended existing contact IDs. Report the stale header buyer as blocked if safe contact replacement is not available.
- For BC CPS, page indexes can shift if information pages are included. Verify visible signature/initial pages when extracting signature status.
- Do not treat browser script exit code or a button click as completion; verify SkySlope transaction status and checklist row statuses after every write/upload.
- LTSA/title-charge document handling: a Drive title-search PDF that lists legal notations/charges is only the index/source, not the ordered charge package. Search Drive for the registration numbers first; if only the title/common-property print appears, the separate instruments still need to be ordered from LTSA.
- LTSA title-charge ordering workflow learned from a strata title-charge run: after authentication, use **Order Documents and Plans** (`https://apps.ltsa.ca/srs/app#/docPlanSearch`) and enter every non-financial legal-notation/charge registration number from the title into `docPlanNumber0...`. Do **not** include mortgages or other financial charges unless the realtor explicitly asks. Only 10 document fields may be visible at first; click **Add More Fields (up to 30)** before filling `docPlanNumber10+`. LTSA may mark duplicate registration numbers as duplicates, e.g. two registration numbers turning out to be duplicates of two others, and will reduce the requested count accordingly. Save the confirm/summary text and screenshot before purchase so the requested docs, duplicates, and total are auditable.
- If the realtor asks to order title charges and provides the MFA/authorization, treat that as approval to attempt the LTSA purchase for those instruments, but still verify the purchase completed and PDFs downloaded/saved before saying it is ordered. If LTSA returns **insufficient funds in deposit account**, report the exact total and ask the realtor to fund the deposit account; do not retry purchase until funds are added.
- After LTSA purchase succeeds, do **not** re-buy missing downloads. Go to the LTSA inbox/documents folder (`https://apps.ltsa.ca/gateway/#/home` → **See all in inbox**) and open the latest matching inbox item by file reference/subject. For a multi-document purchase, the inbox item subject lists the documents, has a **Download All** control, and may save each PDF by registration number. For a separately purchased/late item such as `Document KN111910`, open that inbox row and click the individual PDF or Download All. Verify each expected registration number appears in `pdftotext` output before reporting completion.
- When uploading LTSA PDFs to the property Drive folder with `gws`, use `--upload` rather than the obsolete `--media` flag. In non-interactive/background runs, set `GOOGLE_WORKSPACE_CLI_KEYRING_BACKEND=file` if gws fails with macOS keyring “User interaction is not allowed.” Example: `GOOGLE_WORKSPACE_CLI_KEYRING_BACKEND=file gws drive files create --json '{"name":"<property address> Title Charge - KN111907.pdf","parents":["FOLDER_ID"],"mimeType":"application/pdf"}' --upload /path/KN111907.pdf --upload-content-type application/pdf`.
- LTSA may require SMS/phone 2FA after username/password login. Stop at the verification-code screen and ask the realtor for the code; do not claim the instruments were ordered until the order/download completes and each registration-number PDF is saved to the property Drive folder.
- SkySlope transaction checklist row verification is not enough when a row already shows **In Review**. Open the exact attach page for that row and verify the intended file name appears in the page text or hidden `HFFileName` value. In one strata deal, row 9 already showed In Review before adding the remuneration disclosure, and final verification came from `HFFileName` including a filename that matched the disclosure and offer amount.
- If a SkySlope attach page lists existing documents and there is no visible upload/save button after setting a file, inspect hidden fields and page text before assuming failure; the file may already have been staged/attached. Re-open the checklist and attach page to verify the file name and correct row.
- For a superseding accepted-offer upload where the SkySlope transaction header still shows stale older-offer terms, do not use the header alone as failure proof. Verify the exact checklist attach page for the row, especially hidden `ContentPlaceHolder1_HFFileName`, and the Documents tab row. In one Offer 2 run, the CPS attach page for `SingleTransactionFileUpload.aspx?...Process=T&Index=3` showed `HFFileName` containing the property-and-offer-labeled accepted-offer filename, and the Documents tab showed the same file with a matching DocumentServiceKey, even though the header still showed older sale price/buyer/date values.
- For an Offer 2 row 9 / “Disclosure to Sellers of Expected Remuneration” case, row status **In Review** plus hidden `HFFileName` containing a property-and-offer-labeled remuneration-disclosure filename is necessary but not final proof if the checklist `opendoc(...)`/Documents-tab link does not show the exact filename. Treat that as **partial verification**: reopen the row attach page and Documents tab in a fresh session, confirm the actual document-store link/metadata maps to the same filename, and only retry upload if the file-store proof is missing. Do not final-submit compliance or notify externally during this verification pass. If the viewer already shows multiple Offer-2-stem remuneration disclosure attachments, do not upload another duplicate; report the duplicate count and verify the current visible/document-store link instead.
- For an Offer 2 SkySlope commission/header correction, the transaction header can show corrected Offer 2 sale price/acceptance/close while still showing stale buyer contact text from the old accepted offer.
